When using a Docker development environment, you write code on your host machine (your regular computer OS) using your favorite code editor or IDE, and you sync that code into the Docker container in real time. You almost never write code inside the container directly. [1, 2] 
There are two main methods to achieve this workflow.
------------------------------
## Method 1: The Modern & Seamless Way (VS Code Dev Containers)
If you use [VS Code](https://code.visualstudio.com/), you can use the official [VS Code Dev Containers extension](https://code.visualstudio.com/docs/devcontainers/containers). [3] 

   1. How it works: VS Code automatically spins up your Docker container, installs a lightweight server inside it, and connects your editor to it. [4] 
   2. The Experience: You write code in VS Code just like normal. However, when you open the integrated terminal, you are instantly typing inside the Linux container. Any extensions you use (like Python or Node debuggers) run directly inside the container, utilizing its isolated languages and tools. [5, 6, 7] 

## Method 2: The Traditional Way (Docker Volumes)
If you prefer tools like IntelliJ, PyCharm, Sublime Text, or Neovim, you use Docker Volumes to mirror your project files. [8, 9] 

   1. Bind Mounting: When you launch your container, you use a flag (-v) or a docker-compose.yml file to "mount" your local project directory into a folder inside the container.
   * Command line example: docker run -v $(pwd):/app -p 3000:3000 my-image [2, 6, 8] 
   2. The Code Loop:
   * You open the project folder locally in your IDE and edit files.
      * The moment you hit Save, Docker instantly mirrors those changes into the running container.
      * If your app has a tool like nodemon or web dev hot-reloading turned on, the container will instantly refresh and show your changes. [2, 10] 
   
------------------------------
## Comparison: How the workflows stack up

| Feature | Method 1: VS Code Dev Containers | Method 2: Traditional Volumes |
|---|---|---|
| Where you type | In VS Code (connected directly to the container) | In any IDE/Editor on your local machine |
| Where Extensions/SDKs run | Isolated completely inside the container | On your local machine (IDE needs local access) |
| Terminal access | Integrated terminal is inside the container | Separate terminal window required via docker exec -it |
| Best For | Zero-config setups, keeping local machine 100% clean | Custom IDEs, lightweight setups, legacy projects |

## Best Practices for Writing Code in Docker

* Use Live-Reloading: Ensure your app's start command uses a development flag that watches for file changes (e.g., --reload for FastAPI, nodemon for Node) so you don't have to restart the container every time you change a line of code. [10] 
* Forward Your Ports: Always map the container's internal port to your local machine (e.g., -p 8080:8080) so you can open localhost:8080 in your regular web browser to test your changes. [2, 11] 
* Handle Dependencies Wisely: If you install a new package (like running npm install or pip install), do it via a terminal connected inside the container so it targets the correct operating system environment. [2]

You should use Docker for both local development and production.
While it is technically possible to only use Docker for production, running Docker locally solves the infamous "it works on my machine" problem. If you only use Docker for production, you risk writing code that works perfectly on your local computer but breaks the moment it deploys to the server.
------------------------------
## The Verdict: Why Docker is worth it locally
Using Docker across both environments ensures that your development, staging, and production setups are identical.

| Feature | Without Docker Locally | With Docker Locally |
|---|---|---|
| Environment Parity | Local OS (e.g., macOS/Windows) differs from production (Linux). Causes hidden bugs. | Local environment is identical to production (Linux). Bugs are caught early. |
| Onboarding New Devs | Hours or days spent installing databases, language versions, and tools. | One command (docker compose up) and the entire app runs instantly. |
| Dependency Conflict | Hard to manage if Project A needs Node 16 and Project B needs Node 20. | Each project has its own isolated container and dependencies. |
| Database Management | You must manually install, configure, and run Postgres, Redis, etc., on your OS. | Spin up exact database versions in seconds without cluttering your main OS. |

------------------------------
## The Trade-offs (The "Catch")
While local Docker is highly recommended, it does come with a few minor hurdles you should be aware of:

* Performance Overhead: Docker runs inside a lightweight virtual machine on macOS and Windows. This can cause slower file-syncing and higher RAM usage compared to running code natively.
* Learning Curve: Your team needs to understand basic Docker concepts, volumes, and network port forwarding.

## When it is okay to skip Docker locally
You can skip local Docker if you are building a simple, standalone frontend application (like a basic React or Vite app) that doesn't rely on complex databases or backend languages. In those cases, a simple npm run dev locally is usually perfectly fine, even if the final build is containerized for production.

Instead of creating separate Dockerfiles for dev and prod, you write one Dockerfile with multiple "stages." This guarantees that both environments share the exact same base OS and core system libraries.

# --- Stage 3: Production Build Environment ---FROM base AS production# Only install production-necessary dependenciesRUN npm ci --only=productionCOPY . .# Prune or build assets if needed (e.g., Next.js build or Vite build)CMD ["npm", "run", "start"]

## Step 2: Create a docker-compose.yml (For Local Devs)
Your developers will never run raw docker build or docker run commands. Instead, you hand them a docker-compose.yml file. This acts as a single configuration file that manages their app container, their database, and their local code syncing.

      target: development # 👈 Tells Docker to stop at the 'development' stage above

    volumes:

Explain to me the local setup in more detail and how it works

To understand how the local Docker setup works, it helps to look at it as a live, real-time bridge between your developer’s physical laptop (the host) and an isolated, virtualized Linux operating system (the container).
When a developer types docker compose up, Docker configures three core mechanisms to make coding seamless: Bind Mounts (file syncing), Port Forwarding (network access), and Internal Networking (database connectivity).
Here is exactly how those components interact behind the scenes during a local coding session.
------------------------------
## 1. File Syncing via "Bind Mounts" (How code edits update instantly)
The biggest misconception is that you have to rebuild your Docker image every time you change a line of code. You don't. This is solved by the volumes: block in your docker-compose.yml file:

volumes:
  - .:/app


* The Host Side (.): This represents the exact folder on the developer's laptop where the project code lives.
* The Container Side (/app): This is the folder inside the virtual Linux container where the application runs.

How it works in real-time:
When the container starts, Docker "mounts" (links) the local project folder directly over /app. If a developer opens VS Code on their Mac, edits server.js, and presses Ctrl+S, that file change instantly reflects inside the Linux container.
If the application is running a tool that watches for file changes (like nodemon for Node, uvicorn --reload for Python, or Air for Go), the app detects the modified file inside /app and restarts the process automatically. The developer never manually restarts Docker.
------------------------------
## 2. Port Forwarding (How devs view the app in their browser)
By default, a Docker container is a locked box. If your app starts up inside the container on port 3000, a developer typing localhost:3000 into their regular Chrome browser will get a "Site cannot be reached" error.
This is solved by the ports: block:

ports:
  - "3000:3000"


* The Left Side (3000): The port on the developer's actual laptop (Host).
* The Right Side (3000): The port the web server is listening to inside the container.

How it works in real-time:
Docker sets up a network proxy. When a developer goes to http://localhost:3000 in their local browser, Docker catches that traffic on the laptop and routes it directly into the container's port 3000.
------------------------------
## 3. Internal Networking (How the app talks to the database)
In a traditional setup without Docker, a developer has to install Postgres on their Mac/Windows machine, make sure it runs as a background service, and connect to it via localhost:5432. If one developer has Postgres 13 and another has Postgres 16, bugs happen.
With Docker Compose, you define the database as a separate service right next to the web app:

services:
  web:
    # ... application setup
    environment:
      - DATABASE_URL=postgres://user:pass@db:5432/mydb
  db:
    image: postgres:15-alpine

How it works in real-time:
When Docker Compose spins up these services, it automatically creates a private, isolated virtual network just for them.

* Inside this network, Docker runs a mini DNS server.
* The web app container doesn't look for the database on localhost. Instead, it looks for the hostname db (which matches the name of the service in the YAML file).
* Docker automatically resolves db to the private IP address of the Postgres container. The developer didn't have to install a single database file on their actual computer.

------------------------------
## The Complete Local Developer Lifecycle (Step-by-Step)
To see how clean this makes your onboarding and daily workflow, look at the lifecycle for a developer on your team:

   1. Day 1 Onboarding: A new developer clones the git repository. They install nothing on their machine except Git and Docker Desktop. They run docker compose up. Within two minutes, the app and the database are fully configured and running.
   2. Daily Coding: The developer opens their favorite IDE on their laptop. They edit code. The code changes immediately sync into the container via the Bind Mount. The application hot-reloads inside the container.
   3. Testing the App: The developer opens Chrome on their laptop and navigates to localhost:3000. Port Forwarding routes them straight into the containerized app.
   4. Installing a New Package: If they need to install a new dependency (e.g., a new npm package or pip library), they don't run it locally. They open a terminal into the running container by typing docker compose exec web npm install <package-name>. This ensures the library is downloaded and configured specifically for the container's Linux OS, preventing architecture mismatches (like a Mac M3 trying to run a x86 binary).

Explain to me docker compose it seems really handy for this local dev use case

Docker Compose is exactly what turns Docker from a complex, frustrating tool into an incredibly handy local development experience.
Think of a standard Dockerfile as a recipe for a single ingredient (like just your web app, or just your database). Docker Compose is the master recipe that brings all those ingredients together, coordinates them, and cooks the entire meal with a single command.
Without Docker Compose, managing a local multi-container development environment is a nightmare of long, unreadable terminal commands.
------------------------------
## The Problem: Life Without Docker Compose
If your app needs a web server and a Postgres database, you would have to open your terminal and manually type these two massive commands every single morning:

# 1. Start the database container manually
docker run --name my-local-db -e POSTGRES_PASSWORD=secret -p 5432:5432 -d postgres:15-alpine
# 2. Build and start the web app container manually, linking it to the network
docker build -t my-web-app .
docker run --name my-web-app -p 3000:3000 -v $(pwd):/app --network host -e DATABASE_URL=postgres://postgres:secret@localhost:5432/mydb my-web-app

Your developers would have to memorize these flags, type them in the exact right order, and manually clean them up when they are done. It is prone to human error and breaks down instantly as your stack grows.
------------------------------
## The Solution: Life With Docker Compose
Docker Compose replaces all of that manual command-line overhead with a single configuration file named docker-compose.yml.
Instead of typing commands, you define your infrastructure as code. You check this file directly into your Git repository so every engineer on your team shares the exact same setup.
Once that file is in place, the developer's daily workflow shrinks down to just two simple commands:

* docker compose up — Spins up the database, creates the network, links your local code volume, builds your app, and starts everything simultaneously.
* docker compose down — Gracefully stops all containers, tears down the virtual network, and frees up your laptop's RAM and CPU.

------------------------------
## Why it is uniquely powerful for Local Dev
Docker Compose includes specific features designed precisely for a local engineering workflow:
## 1. Visual Logs in One Terminal
When you run docker compose up, it merges the log streams from all your different containers into a single terminal window. It color-codes them by service, so you can watch your frontend, backend, and database interact in real-time as you write code.
## 2. Automatic Dependency Ordering
If your web app tries to start up before your database is ready, your app will crash with a connection error. Docker Compose handles this with a simple depends_on tag:

services:
  web:
    build: .
    depends_on:
      - db # 👈 Tells Compose to fully launch the database container first
  db:
    image: postgres:15-alpine

## 3. Persistent Data (Named Volumes)
By default, Docker containers are ephemeral—if a container stops, everything inside it is wiped out. You don't want your developers losing all their test data every time they reboot their laptops. Docker Compose lets you define a named volume for your database:

services:
  db:
    image: postgres:15-alpine
    volumes:
      - db_data:/var/lib/postgresql/data # 👈 Saves DB data onto the laptop's disk
volumes:
  db_data: # 👈 Outlives the lifecycle of the container

Now, if a developer restarts their computer or updates the Docker container, their local test accounts, seeds, and database schemas remain perfectly intact.

What is the rag flow to each agent look like with this architecture?

The RAG (Retrieval-Augmented Generation) flow within this multi-tenant, isolated-compute architecture must be split into two separate phases: The Ingestion Pipeline (handling the uploaded data via the control plane) and The Runtime Query Loop (handling the real-time streaming chat widget).
Because your architecture utilizes pooled database storage but siloed compute runtimes (LangGraph pods), security and tenant boundaries must be strictly enforced at every transition point. [1, 2] 
------------------------------
## Phase 1: The Ingestion Pipeline (Asynchronous Data Upload)
When a business user logs into their dashboard and uploads a document (e.g., a refund policy PDF), it passes through the shared Control Plane to ensure the business's laptop/browser never directly touches your internal database keys.

[Dashboard UI] ──(Upload PDF)──> [Control Plane API]
                                         │
                 ┌───────────────────────┴───────────────────────┐

  Path: s3://tenant-123/docs/policy.pdf                         │ (Generate Vectors)
                                                                 ▼
                                                      [Shared Vector Store]
                                               Inserts payload with metadata:
                                               { "tenant_id": "tenant-123", ... }


   1. Upload & Guardrails: The Control Plane API authenticates the user, reads their session to fetch their unique tenant_id (e.g., tenant-123), and uploads the raw document into an isolated folder inside AWS S3 (s3://my-bucket/tenant-123/).
   2. Chunking & Embedding: The Control Plane splits the document into smaller, semantic text chunks. It passes those text chunks to your embedding model (e.g., OpenAI or Hugging Face) to convert the text into numerical vectors. [3, 4] 
   3. Inserting with Hard Metadata Filters: The text chunks and vector embeddings are written to your shared Vector Database. Crucially, every single record is forced to include a strict tenant_id payload attribute. [1, 3, 5] 
   
   {
     "vector": [0.134, -0.432, ...],
     "payload": {
       "tenant_id": "tenant-123",
       "text_content": "Our return policy lasts exactly 30 days...",
       "source_file": "policy.pdf"
     }
   }

## Phase 2: The Runtime Query Loop (The Agentic RAG Flow)
When an end-user visits a client's website and opens the embeddable chat widget, the request goes directly to the tenant's dedicated, isolated LangGraph pod to process the response.

## Step 1: Secure Ingress Routing
The reusable chat widget wakes up on the customer's page and connects back to your cloud via a persistent connection (WebSocket or Server-Sent Events for streaming answers).

* 
* The connection payload contains the text query and a client-specific public API key.
* Your AWS EKS Ingress Controller (e.g., Traefik or Kong) intercepts the request. It validates the API key, matches it to tenant-123, and routes the network traffic directly into the isolated Kubernetes namespace/pod running the LangGraph Agent for Tenant 123. [2] 
* 

## Step 2: The LangGraph Inner Agent Loop
Inside that isolated pod, your LangGraph orchestration engine takes over. Instead of a basic sequential RAG query, the agent behaves as a multi-step state machine: [6, 7] 

   1. Intent Node: An initial LLM node analyzes the user's message. If the user asks something general like "Hello", the graph completely skips the database step to save latency and costs. If they ask "How do I return this shirt?", the graph triggers its defined Knowledge_Base_Retrieval Tool. [7, 8] 
   2. The Retrieval Tool Execution (The Multi-Tenant Guardrail): The pod calls your centralized Vector DB. The isolated pod explicitly injects its own hardcoded tenant identifier into the query filter.
   * The database query logic: Search vectors matching 'return shirt' WHERE payload.tenant_id == 'tenant-123'.
      * Because of this query constraint, there is zero risk of cross-tenant leakage. Even if a mathematical error places Tenant B's vectors close to Tenant A's, the database filter drops Tenant B's documents automatically before returning results. [1, 7, 9] 
   3. Memory Checkpointing: Simultaneously, another LangGraph node queries its local checkpointer (like an isolated Redis cache or local SQLite file attached only to that pod) to pull the history of this specific user's chat session. This ensures the agent remembers things like "The user mentioned they bought the shirt yesterday" across messages. [10] 

## Step 3: Synthesis & Streaming
The retrieved document chunks and past conversation history are fed back into the LangGraph state. [11] 

* 
* The final LLM generation node compiles the system instructions ("You are a helpful customer support agent for...") along with the dynamically fetched context, and requests a response from the foundation model. [5, 11] 
* As the LLM generates tokens, the isolated pod immediately streams those individual text tokens out through the network proxy straight to the user’s embeddable chat widget, creating a fast, typing-animation effect.
* 

------------------------------
## Key Advantages of This Split Flow

* 
* Security at the edge: The isolated pod only knows its own tenant_id. It doesn't have master credentials to view other data.
* Cost Efficiency: You aren't paying for 50 separate Vector Database licenses; you run one scalable cluster but isolate data using native metadata fields.
* Resilience: If one business's widget receives a traffic spike (a "noisy neighbor"), only their dedicated Kubernetes pod experiences CPU load. The other client pods remain completely unaffected. [1, 9]

ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

* **Vector Database:**
* **Phase 2 Target:** Managed Qdrant Cloud, Pinecone, or AWS OpenSearch.
* **Scaling Mechanism:** Managed cluster sharding. Qdrant uses payload indexing on `tenant_id` so vector searches filter by tenant before computing similarity vectors, keeping latency low under multi-tenant load.

The control plane handles ingestion, user management, authentication, and admin tasks.

* **Auto-Scaling Metric:** Configure a Horizontal Pod Autoscaler (HPA) targeting **CPU/Memory utilization** (e.g., scale out when average CPU > 70%) or **HTTP request count per target**.
* **Asynchronous Processing:** For heavy ingestion jobs (chunking, embedding generation), offload execution from HTTP handlers to a background worker pattern (e.g., Celery/Redis, BullMQ, or AWS SQS + Lambda).

## 1. Architecture Changes: Context & Request Flow

In Phase 1, `TENANT_ID` is injected static from `.env`. In Phase 2, `TENANT_ID` must be **dynamically derived per request**. Your architecture must handle this transition without changing function signatures.

```
[Chat Widget / Dashboard]
       │  HTTP / WS Header: Authorization: Bearer <JWT>  (OR X-Tenant-ID in dev)
       ▼
[API Gateway / Control Plane] ──► Decodes JWT, extracts tenant_id
       │
       ├──► Inject into Postgres Session: SET LOCAL app.current_tenant_id = '...'
       │
       └──► Forward to Agent Service with Header: X-Tenant-ID
               │
               └──► Agent Context / Retrieval Tool Filters (tenant_id == '...')

```

### Required Changes:

1. **API Gateway / Middleware Layer:**
* **Phase 1:** Middleware extracts `process.env.TENANT_ID` (or `os.getenv("TENANT_ID")`) and sets it on every request context (`req.tenantId` or FastAPI `request.state.tenant_id`).
* **Phase 2:** The *exact same middleware* is modified to extract `tenant_id` from a decoded JWT payload or incoming request header (`X-Tenant-ID`). **No downstream business code changes.**


2. **Database Connection Pooling:**
* Instead of maintaining tenant-specific connection pools, use a shared connection pool (e.g., PgBouncer / AWS RDS Proxy). For Postgres RLS to work smoothly, wrap queries in a transaction block that sets session state:
```sql
BEGIN;
SET LOCAL app.current_tenant_id = 'tenant_123';
SELECT * FROM documents WHERE ...;
COMMIT;

```

## 2. Interface Changes: Abstractions & Code Contracts

You must define three clear code abstractions in Phase 1 so swapping implementation drivers in Phase 2 requires **zero updates to business logic**.

### A. Storage Interface (`StorageService`)

Abstract file uploads, downloads, and presigned URLs behind a uniform class contract.

* **Interface Signature:**
```python
from abc import ABC, abstractmethod
from typing import BinaryIO

class StorageService(ABC):
    @abstractmethod
    async def upload_file(self, file_obj: BinaryIO, path: str, tenant_id: str) -> str:
        """Uploads file and returns absolute URI / identifier."""
        pass

    @abstractmethod
    async def get_presigned_url(self, path: str, tenant_id: str, expires_in: int = 3600) -> str:
        """Generates direct read/write URL for client uploads."""
        pass

```

What about scaling the backend server itself?

To scale the **backend server** (`backend-core`) itself from Phase 1 (a single Docker container running on `docker-compose`) to Phase 2 (handling thousands of concurrent tenant requests), you must transition it from a monolithic, stateful-style execution model into a **stateless, horizontal auto-scaling service mesh**.

Here is the step-by-step breakdown of how to scale the backend server, the required code patterns, and the infrastructure needed.

---

## 1. Architectural Rules for Backend Server Scaling

To allow your backend server to scale horizontally (adding more instances/containers on demand behind a load balancer), it must strictly adhere to three rules:

### Rule 1: Zero Local State (Stateless Server)

* **No Local In-Memory Sessions:** Store user sessions, auth states, and tokens in a shared, centralized cache like **Redis / AWS ElastiCache**—never in server memory.
* **No File Persistence on Disk:** File uploads and PDF parsing must use stream buffers or temp storage before shipping directly to S3 via your `StorageService` interface.

### Rule 2: Decouple Synchronous APIs from Heavy Ingestion Jobs

Do not execute heavy document parsing, chunking, or vector embedding generation within HTTP request/response loops.

* **Phase 1:** Run background tasks locally using a simple task queue (e.g., Celery, BullMQ, or FastAPI `BackgroundTasks`).
* **Phase 2:** Offload jobs to an asynchronous message broker (e.g., **AWS SQS / RabbitMQ / Redis**). The HTTP API returns `202 Accepted` immediately, while dedicated worker pods pick up jobs asynchronously.

### Rule 3: Database Connection Pooling & Thread Safety

When 50 backend containers scale up to handle load, they can quickly overwhelm your Postgres database with hundreds of simultaneous connections.

* Put a connection pool manager like **PgBouncer** or **AWS RDS Proxy** between the backend server instances and your Postgres database.

## 2. Infrastructure Scaling Pattern (Phase 1 vs. Phase 2)

```
[ Incoming Requests ]
         │
         ▼
[ AWS Application Load Balancer (ALB) ]
         │
  ┌──────┴───────────────────────────┐
  ▼                                  ▼
[ backend-core Pod 1 ]      [ backend-core Pod 2 ] ... [ Pod N ] (Scales via HPA)
  │      │                           │
  │      └───────────┬───────────────┘
  ▼                  ▼
[ Redis / Cache ]  [ Managed Postgres / Aurora ] (Shared State & Data)

```

| Dimension | Phase 1 (Local Stack) | Phase 2 (Production Scale) |
| --- | --- | --- |
| **Compute Platform** | Single `docker-compose` container | **AWS EKS Deployment** (Kubernetes) or AWS ECS Fargate |
| **Traffic Routing** | Direct Docker port expose (`:8080`) | **AWS Application Load Balancer (ALB)** with HTTPS Termination |
| **Scaling Trigger** | Manual / Static | **Horizontal Pod Autoscaler (HPA)** based on CPU/RAM or RPS |
| **Session & State** | In-memory / Single Instance | **AWS ElastiCache (Redis)** |
| **Job Offloading** | Synchronous / Local Threads | **AWS SQS + Worker Pod Pool** |

## 3. Kubernetes HPA Configuration for `backend-core`

In Phase 2, when deploying `backend-core` to Kubernetes (EKS), you use a **Horizontal Pod Autoscaler (HPA)** manifest. This automatically adjusts the number of replica pods based on traffic or system load.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: backend-core-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: backend-core
  minReplicas: 2          # High Availability minimum
  maxReplicas: 20         # Scales up under peak load
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70   # Spawns new pods when CPU > 70%
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80

```

## 4. Asynchronous Heavy Ingestion Architecture

Scaling the HTTP backend requires separating **API handlers** from **heavy worker processes**:

```python
# FastAPI Example (backend-core API endpoint)

@router.post("/api/v1/documents/ingest")
async def ingest_document(
    file: UploadFile,
    tenant_id: str = Depends(get_current_tenant_id),
    queue: QueueService = Depends(get_queue_service)
):
    # 1. Upload raw file to S3 storage abstraction immediately
    file_path = await storage_service.upload_file(file.file, file.filename, tenant_id)
    
    # 2. Push ingestion job payload to SQS/Redis Queue (Fast, <50ms response)
    job_id = await queue.enqueue_job(
        task_name="process_rag_document",
        payload={"file_path": file_path, "tenant_id": tenant_id}
    )
    
    # 3. Return 202 Accepted instantly to keep API responsive
    return {"status": "processing", "job_id": job_id}

```

* **API Pods (`backend-core`):** Process web requests, serve dashboard APIs, and enqueue tasks.
* **Worker Pods (`backend-worker`):** Pull tasks from the queue, chunk PDFs, generate embeddings, and write to Qdrant/pgvector. These worker pods scale independently based on queue length (e.g., using **KEDA - Kubernetes Event-driven Autoscaling**).
